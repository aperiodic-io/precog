# Commit tiny cuts, keep the leaderless write path

Scalog-style cuts remain the best way to add a total order to precog, with two changes to the textbook design. First, the cut should be indexed by **origin node** (a 3-entry vector of durable WAL frontiers), not by writer log. Second, precog should keep its current "ack at 2 of 3, bind position later" contract, which is LazyLog's semantics, and gate only *ordered* readers on the committed cut. No alternative is both simpler and stronger. Per-key or per-writer order is simpler and costs nothing, but it is not a total order. A round-based deterministic merge, or node-stamped HLC plus watermarks, removes the per-cut Raft commit from steady state. In exchange it stalls every ordered reader whenever any node is slow or dead, and it needs a separate, rarely exercised seal path. Token sequencers (Corfu, Tango, Delos NativeLoglet) put a round trip and a 0.2–0.6M/s ceiling in front of every append. That gives up the property that makes precog fast. Every total-order scheme needs consensus *somewhere*, because total order broadcast is equivalent to consensus ([Défago et al.](https://infoscience.epfl.ch/record/49913/files/DSU03b.pdf)). The design question is therefore only where that consensus runs and how often. Committing one small vector every T ms answers it with the least new machinery. The recommended plan has three phases. Phase 0 makes per-writer order the default contract. Phase 1 adds origin-node cuts with a per-writer FIFO fix-up and an optional ordered-ack. Phase 2 adds SpecLog-style speculative delivery only if the ordered feed's latency matters. The main correctness risks are not in the cut itself. They sit in five places: per-writer order across failover, duplicate retries that land on two nodes, the definition of "durable frontier" under 2-of-3 replication, real-time order (which lazy acking does not give), and stale or lease-less nodes acting on cuts.

## Consensus is unavoidable, so the real choice is its frequency

The theory settles what can be avoided. Total order broadcast and consensus are equivalent, and by FLP neither has a deterministic solution in an asynchronous system with even one crash ([Défago, Schiper, Urbán §2.4.5](https://infoscience.epfl.ch/record/49913/files/DSU03b.pdf)). The survey says flatly that claims to solve total order "in asynchronous systems with process failures" are "of course incorrect ... or incomplete at best" ([Défago et al. §2.5](https://infoscience.epfl.ch/record/49913/files/DSU03b.pdf)). What *can* be avoided is consensus per message. Communication-history algorithms deliver in a deterministic order once they have heard from every member. They need agreement only when membership changes and the system must fix exactly what a departed member contributed ([Défago et al. §7.4, §8](https://infoscience.epfl.ch/record/49913/files/DSU03b.pdf)). Kleppmann's summary states the trap both simple approaches fall into: "the crash of a single node can stop all other nodes from being able to deliver messages" ([Kleppmann notes](https://www.cl.cam.ac.uk/teaching/2122/ConcDisSys/dist-sys-notes.pdf)).

Three different guarantees get conflated under "ordering," and they cost different amounts. **Total order agreement** means every reader sees the same cross-writer sequence. **Finality** means a delivered prefix never changes after a crash. Both need a consensus-decided frontier, either on every cut (Scalog) or only on each failure (rounds, watermarks, Mencius revocation). **Real-time order** means that if A is acked before B is issued, then A precedes B. It needs more: either the ack waits until A's position is fixed, or the system waits out a clock-uncertainty bound, as Spanner's commit wait does ([Spanner OSDI'12](https://static.googleusercontent.com/media/research.google.com/en//archive/spanner-osdi2012.pdf)). Precog acks before any ordering exists, so today it gives durability and per-writer FIFO but neither total order nor real-time order across writers. Its current fallback of merging by source event time is a deterministic merge with no completeness criterion. A late record with an older timestamp can reorder history, so no prefix is ever final ([Kleppmann notes, SEC discussion](https://www.cl.cam.ac.uk/teaching/2122/ConcDisSys/dist-sys-notes.pdf)).

Precog is already the hard half of a modern shared log. Narwhal's central insight is to split "reliable transaction dissemination from transaction ordering," so that consensus orders only references. That raised HotStuff from 1.8k to over 130k tx/s ([Narwhal & Tusk](https://arxiv.org/abs/2105.11827)). Scalog makes the same split under crash faults: storage servers replicate FIFO segments, and a Paxos group orders only integer vectors ([Scalog NSDI'20](https://www.usenix.org/system/files/nsdi20-paper-ding.pdf)). Precog's per-node group-commit WAL, replicated directly to peers and durable at 2 of 3, *is* that dissemination layer. "Durable at 2 of 3" plays the role that availability certificates play in DAG-BFT, so the BFT machinery of Bullshark and Mysticeti buys nothing under crash faults.

## Ten options scored against precog's five criteria

The table ranks each option on top of precog as it exists. Latency is the delay *added to ordered delivery*. Write-path effect assumes precog keeps acking at 2 of 3. Latency formulas are derived from the cited mechanisms and are estimates, not published figures: d is the one-way delay, T or R the cut or round interval, C one Raft commit, and ε the clock-error bound.

|---|---|---|---|---|---|
| **Per-key / per-writer order** (Kafka, S2) | Already exists | 0 (the durability ack only) | None | Per-writer FIFO, final; no cross-writer order | No ordering stall |
| **Scalog cuts over origin-node frontiers**, lazily bound | Moderate: 3-node Raft + deterministic expander | ≈ T/2 + d + C + d (estimate ≈ 2–5 ms at T=1–2 ms) | None on the ack path; a Raft outage stalls only ordered reads | Total order, final; real-time only with optional ordered-ack | Slow or crashed data node does not stall others; Raft leader loss stalls cuts for one election |
| **Round-based deterministic merge** (Mencius/Calvin without per-slot Paxos) | Moderate; two code paths (steady state + seal) | ≈ R/2 + d_max + durability lag (estimate ≈ 1–3 ms) | None; all-to-all round-close messages | Total order, final; real-time with a round-close ack wait | Any slow or silent node stalls all ordered readers until detection + Raft seal |
| **Node-stamped HLC + durable watermarks** (CRDB closed ts, TiKV resolved ts) | Same as rounds, plus clock handling and re-stamping | ≈ watermark interval/2 + d_max + skew | None; periodic idle heartbeats | Total order, final; real-time within ε with a commit wait | Same min-watermark stall; a bad clock breaks real-time order, not agreement |

| **Leaderless dependency SMR** (Accord, Tempo, EPaxos) | Heavy: quorum rounds per command, complex recovery | ≥ 1 quorum RTT per command | Per-message coordination | Strict serializability | Complex recovery |

### Scalog wins on failure behaviour, not on raw latency

Scalog's mechanism works as follows. Storage servers periodically report a *local cut*, which is the count of durable records per segment. The ordering layer commits a *global cut*, and positions follow from a deterministic interleaving of consecutive cuts. Holes are impossible because cuts only count records that are already durable ([Scalog](https://www.usenix.org/system/files/nsdi20-paper-ding.pdf)). The prototype reached **255K totally ordered writes/s** on 17 shards. Emulation suggested about **52M writes/s at about 1.6 ms** with a 0.1 ms interleaving interval. When the Paxos leader failed, "Scalog suffers no net throughput loss": servers kept storing records and throughput spiked to catch up after re-election ([Scalog](https://www.usenix.org/system/files/nsdi20-paper-ding.pdf)). The decisive property for precog is that **the committed cut decides what is in**. A crashed or GC-paused data node simply contributes no new records to the next cut, and nobody waits for it. Each segment advances at the speed of its own durable copies. In min-watermark and round-merge schemes, by contrast, the slowest node gates *everyone*. A silent node blocks delivery until the survivors run a consensus-backed seal. Mencius's authors say of their own design that it "temporarily stalls when any of the servers fails while Paxos temporarily stalls only when the leader fails" ([Mencius OSDI'08](https://www.usenix.org/legacy/event/osdi08/tech/full_papers/mao/mao_html/)). Production watermark systems confirm that this is a live operational problem and not a theoretical one. TiCDC ships alerts for a resolved ts stuck for more than 1 minute ([TiCDC alert rules](https://docs-archive.pingcap.com/tidb/v7.3/ticdc-alert-rules/)). Flink's `withIdleness` escape hatch gives up correctness by treating an idle input's late data as late ([Flink docs](https://nightlies.apache.org/flink/flink-docs-stable/docs/dev/datastream/event-time/generating_watermarks/)).

Scalog's cost is one consensus commit per interval. With an origin-node index, each commit carries a 3-integer vector, and 1,000 commits/s at T = 1 ms is trivial load for a 3-node Raft group. Throughput is not at stake. FoundationDB and Scalog both show that a batched singleton orderer is not the ceiling; the ceiling is the metadata payload per commit ([Scalog](https://www.usenix.org/conference/nsdi20/presentation/ding); [FDB read/write path](https://apple.github.io/foundationdb/read-write-path.html)). On ordered-delivery latency the round merge does win, by roughly one Raft RTT in the failure-free case. It pays that back with interest the first time any node pauses.

### Round merge and HLC watermarks are one design with two clock types

The round-based merge orders by (round, node, seq). Each node closes numbered rounds and broadcasts a durable round-close message, including empty ones when idle. A reader delivers round r once every member has closed it. This is Calvin's 10 ms epoch interleave ([Calvin](https://cs.yale.edu/homes/thomson/publications/calvin-sigmod12.pdf)) and Mencius's pre-assigned slots with cheap skips, minus the per-slot Paxos. Node-stamped HLC with watermarks is the same communication-history algorithm with a physical-time-flavoured round number. The CockroachDB closed-timestamp trick carries over directly: a late write is not dropped but **re-stamped above the watermark**, so each node's "I will never stamp ≤ W again" promise is purely local ([CockroachDB follower reads](https://docs.cockroachlabs.com/docs/stable/follower-reads)). Neither design trusts producer clocks. A bad node clock changes *which* order is chosen, but never whether readers agree on it ([HLC tech report](https://cse.buffalo.edu/tech-reports/2014-04.pdf)). Both designs still need a Raft-backed membership service. It must seal a failed node's final round or watermark and fence the node. Otherwise readers that drop the node on independent timeouts will diverge ([Défago et al. §8.2](https://infoscience.epfl.ch/record/49913/files/DSU03b.pdf)).

HLC watermarks offer a cheap route to real-time order. If a node acks A only after its clock passes t_A + ε, any later append at any node gets a larger stamp. On EC2's Nitro PTP clock the reported typical bound is **under 40 µs** ([AWS](https://aws.amazon.com/blogs/compute/its-about-time-microsecond-accurate-clocks-on-amazon-ec2-instances/)), and Meta reports about 436 ns windows of uncertainty ([Meta PTP](https://engineering.fb.com/2022/11/21/production-engineering/precision-time-protocol-at-meta/)). Those waits are far below precog's group-commit time, and since durability usually takes longer than ε the wait is often already satisfied. On generic NTP, where CRDB cites 100–250 ms offsets ([CockroachDB blog](https://www.cockroachlabs.com/blog/living-without-atomic-clocks/)), the wait is prohibitive. A node whose clock silently exceeds ε also silently violates real-time order unless it self-fences. This option is real and inexpensive, but it ties a correctness guarantee to clock infrastructure precog does not control. It works best as a later add-on for deployments with PTP-class clocks.

### Lazy binding is precog's contract already; LazyLog's mechanism is not

LazyLog's abstraction makes an append durable and guarantees that it will "eventually [be] bound to its correct position", with binding done before the position can be read. Readers that lag by about 3 ms see no extra latency ([LazyLog SOSP'24](https://dassl-uiuc.github.io/pdfs/papers/lazylog.pdf)). Precog already behaves this way: it acks at 2 of 3 and has no order yet. Erwin, however, gets linearizability *without* consensus only because every client writes to *all* f+1 sequencing replicas. That makes any replica's log a valid real-time order, but a straggling replica inflates the append tail, and replica failure costs about 15 ms ([LazyLog](https://dassl-uiuc.github.io/pdfs/papers/lazylog.pdf)). Precog acks at 2 of 3 from any node, so that argument does not transfer. The right synthesis is **LazyLog's contract implemented with Scalog's mechanism**.

SpecLog points to the natural Phase 2. It delivers records to consumers with a speculated position computed from predetermined per-shard quotas, and achieves **1.4–1.66× lower end-to-end latency than Scalog** ([SpecLog OSDI'25](https://dassl-uiuc.github.io/pdfs/papers/speclog.pdf)). Its quotas require no-op padding and lease windows, and a naive version loaded the sequencer about 2× more. It is an optimization, not a foundation.

### Sequencers and production metadata commits solve a problem precog doesn't have

Every Kafka-on-object-storage design assigns order after durability through a metadata commit, *and keeps that commit on the ack path*. KIP-1163 targets a coordinator commit of **P50 about 10 ms and P99 20–50 ms** ([KIP-1163](https://cwiki.apache.org/confluence/display/KAFKA/KIP-1163%3A+Diskless+Core)). WarpStream reports that on fast storage "the Control Plane latency dominates", at about 50 ms of a roughly 100 ms budget ([WarpStream Lazy(log)](https://www.warpstream.com/blog/the-art-of-being-lazy-log-lower-latency-and-higher-availability-with-delayed-sequencing)). Ursa runs an Oxia transaction per stream per write ([Ursa VLDB'25](https://www.vldb.org/pvldb/vol18/p5184-guo.pdf)). By default all of them stall or fail produce when the metadata store is down. WarpStream had to bolt on Lightning Topics and Ripcord to ack on durability alone, and gave up offsets at ack time, idempotence and external consistency to do it: "a record acknowledged later can end up with a lower offset" ([WarpStream](https://www.warpstream.com/blog/the-art-of-being-lazy-log-lower-latency-and-higher-availability-with-delayed-sequencing)). **Precog is Lightning Topics by construction.** The lesson to take from these systems is what goes wrong, not what to copy. Jepsen found Bufstream's failures concentrated in the metadata-store integration rather than the ordering logic: stale cached watermarks after restart stalled consumers for over an hour, missed etcd lease deletions stuck producers, and error paths reported offset 0 as success ([Jepsen, Bufstream 0.1.0](https://jepsen.io/analyses/bufstream-0.1.0)). Note also that these systems serialize producers into a partition at commit time. None orders a merged stream of many independent writer logs after the fact, so precog's design has no direct production precedent ([KIP-1164](https://cwiki.apache.org/confluence/display/KAFKA/KIP-1164:+Diskless+Coordinator)).

Token sequencers fail for a simpler reason. Corfu and Tango assign the position *before* the write. Their sequencers top out at **200K tokens/s** (Corfu) and **about 570K/s unbatched** (Tango). A client that takes a token and dies leaves a hole, which Tango fills after 100 ms by default ([Corfu](https://www.usenix.org/system/files/conference/nsdi12/nsdi12-final30.pdf); [Tango](https://www.cs.cornell.edu/~taozou/sosp13/tangososp.pdf)). Delos's NativeLoglet is "unavailable for appends if the sequencer fails" ([Delos OSDI'20](https://www.usenix.org/system/files/osdi20-balakrishnan.pdf)). Precog's crash stall of at most 71 ms and its 2–3.5× durable-throughput lead over Iggy, both from precog's own measurements, come from having nothing on the write path. A per-append sequencer RTT would erase that lead. What *is* worth borrowing from Delos and Boki is the control-plane idea. Boki's metalog uses Scalog's protocol for ordering and Delos's seal for reconfiguration on a 3-replica group, reaching **1.2M appends/s with 6.4 ms p99** ([Boki SOSP'21](https://par.nsf.gov/servlets/purl/10357172)). Delos reports that a sealable, non-consensus loglet took "just under 4 months to implement and deploy" ([Delos](https://www.usenix.org/system/files/osdi20-balakrishnan.pdf)).

Per-key order deserves its top ranking on simplicity. Kafka, the dominant streaming log, deliberately guarantees order only within a topic-partition ([Apache Kafka](https://kafka.apache.org/intro)). S2 offers linearizable per-stream dense sequence numbers, assigned by whichever channel owns the stream ([S2](https://s2.dev/blog/linearizability)). Kleppmann's hierarchy is the precise rule: total order is needed only for non-commutative cross-key state machines, and commutative updates converge under causal or weaker broadcast ([Kleppmann notes](https://www.cl.cam.ac.uk/teaching/2122/ConcDisSys/dist-sys-notes.pdf)). No source quantifies what share of streaming workloads need more than per-key order, so that remains an open product question.

## A three-phase plan that never touches the ack path

**Phase 0: make per-writer order the default contract.** Document that (stream, writer, epoch, seq) order is per-writer FIFO and final at the 2-of-3 ack, and that this is Kafka-equivalent per-key semantics when each key maps to one writer. Stop presenting the source-timestamp merge as an order, since it has no finality. The live feed keeps its 3.3 ms p99 because nothing changes on that path.

**Phase 1: origin-node cuts, lazily bound.** Each node reports, every T ms (start at 1–2 ms), the durable contiguous prefix it holds of *each origin node's* WAL segment, i.e. records that node accepted. A 3-node Raft group, co-located or embedded, computes per origin segment the highest prefix held by at least 2 nodes. It commits the cut ⟨c_A, c_B, c_C⟩ as a monotone vector and broadcasts it. The cut log doubles as a Boki-style metalog: membership changes, epoch seals, node admission at an agreed cut, and trim points all go into the same totally ordered stream. Global order is a deterministic expansion of each cut: by cut number, then origin node ID, then WAL offset, with the per-writer fix-up described below. Ordered readers block on the latest cut and unordered readers are unaffected. The estimated added latency is T/2 plus one report hop, one Raft commit and one fan-out, about 2–5 ms on a LAN. That would put an ordered feed around 5–8 ms p99, still well under Iggy's 18.8 ms live feed. This is an estimate the proof of concept must measure, because no paper reports Scalog at T = 1–10 ms on a 3-node Raft group ([shared-log survey gap](https://www.usenix.org/system/files/nsdi20-paper-ding.pdf)). Offer an opt-in **ordered-ack**: the client's ack waits for the cut containing its record and returns the global position. This is exactly Scalog's ack rule, and it gives linearizability for that client. Any append issued after the ack cannot have been counted in an already-committed cut, so it lands later.

**Phase 2: only if ordered latency is the bottleneck.** There are two levers. SpecLog-style speculation delivers records with a predicted position and confirms it at the cut. HLC commit-wait ordering becomes an option on PTP-class clocks. Do *not* switch the steady state to a round merge with Raft-only-on-failure unless measurements show the Raft RTT dominates. That design saves about one RTT, but it adds a second, rarely exercised seal path ("where bugs would hide") and makes the slowest node everyone's tail.

## Gotchas that will bite first

**Per-writer FIFO breaks across failover unless the expander enforces it.** If seq N is acked via node A and the writer then sends N+1 to node B, B's segment can enter an earlier cut than A's. A plain per-node interleave then places N+1 before N, which breaks both per-writer order and "acked-then-sent". The expander must hold back a record until its (writer, epoch) predecessor has been emitted, carrying it to a later cut. This is still deterministic, because it is a pure function of the cut sequence. Pinning a writer to one node per epoch is the alternative ([shared-log notes on Scalog/LazyLog](https://dassl-uiuc.github.io/pdfs/papers/lazylog.pdf)). The hold-back has a liveness trap. If N was never made durable (in flight to A when A died), N+1 waits forever. The epoch seal or the finalization of A's segment in the metalog must declare N absent. The writer's next epoch then starts cleanly, as in Scalog's emergency finalization, where "the latest cut before s is finalized reveals which" records are in ([Scalog §4.4](https://www.usenix.org/system/files/nsdi20-paper-ding.pdf)).

**Retries create cross-node duplicates.** A writer that times out on A and retries the same seq on B can leave the record durable on both. The expander must deduplicate on (stream, writer, epoch, seq), keeping the first occurrence in cut order. This moves idempotence into the order function, just as KIP-1164 moves producer dedup into the coordinator ([KIP-1164](https://cwiki.apache.org/confluence/display/KAFKA/KIP-1164:+Diskless+Coordinator)).

**"Durable frontier" is not Scalog's element-wise minimum.** Scalog takes the minimum over all replicas of a shard. Under 2-of-3, precog needs the highest *contiguous* prefix held by at least two nodes, which is the second-highest report. Because precog acks on the first peer reply, peers' copies of a segment can be ragged: record r lives on {A, B} and r+1 on {A, C}. Reports must therefore be gap-free prefixes, never "highest seq seen". Cuts must never regress, even when a crashed node's last report is stale. For the same reason, a node must log its own reports (or round-closes) in its WAL before sending them, so that a restarted node cannot contradict itself ([Défago et al. on uniformity](https://infoscience.epfl.ch/record/49913/files/DSU03b.pdf)).

**Lazy acking does not give real-time order, and the API must say so.** Without ordered-ack, a record acked earlier can get a later global position, which is WarpStream's Lightning anomaly ([WarpStream](https://www.warpstream.com/blog/the-art-of-being-lazy-log-lower-latency-and-higher-availability-with-delayed-sequencing)). SpecLog's authors note explicitly that acking before coordination violates linearizability ([SpecLog](https://dassl-uiuc.github.io/pdfs/papers/speclog.pdf)).

**Raft leader placement sets ordered-read failover.** Ingest never stalls. If the crashed data node also hosted the Raft leader, though, ordered delivery pauses for one election timeout. Default-tuned Raft elections can far exceed precog's 71 ms data-path stall, so tune elections to match the data-path failure detector. Fence every cut with the Raft term and membership epoch, so that a node holding a lost lease or a stale cached cut rejects it rather than acting on it. Both failure modes are the ones Jepsen found in Bufstream ([Jepsen](https://jepsen.io/analyses/bufstream-0.1.0)).

**The expansion function is a wire format.** Every reader must compute byte-identical positions. Any change to tie-breaks, hold-back or dedup rules must be versioned in the metalog and switched at an agreed cut, the way Belfast switches quotas only at lease-window boundaries ([SpecLog](https://dassl-uiuc.github.io/pdfs/papers/speclog.pdf)). Ordered readers also buffer up to one cut interval of data per origin. Retention and trim must be expressed in cut positions, so that no node garbage-collects a record that a pending cut still references.

## Conclusion

The question "Scalog or something simpler?" turns out to be the wrong framing. Every candidate that gives a real total order uses consensus. The serious ones (Scalog, Mencius-style rounds, HLC watermarks, Boki) are also all the same "durability first, order frontiers later" idea, and they differ only in *when* consensus runs. Running it on every cut costs about one Raft RTT of ordered latency. In return it buys failure masking: no node's slowness becomes everyone's tail, and there is no second recovery protocol. For a system whose headline advantage is a 71 ms failover against Iggy's multi-second view change, that is the right trade. The less obvious finding is that precog's ack-before-order design, which looks like a liability next to Scalog, is precisely what production systems such as WarpStream had to retrofit for availability. Precog should keep it, push all order-dependent semantics into the cut expander, and treat the per-writer hold-back and dedup rules as the actual hard part of the project.

The open uncertainties are empirical. No published system runs Scalog-style cuts at 1–10 ms intervals on a 3-node Raft group, or over many independent writer logs, so the 2–5 ms estimate needs a proof of concept. That proof of concept should also measure CPU per message on the 4-vCPU box once ordered readers start buffering and expanding. Whether customers need more than per-key order at all is a product question the literature does not answer, and Phase 0 should be shipped and evaluated before Phase 1 is built.
