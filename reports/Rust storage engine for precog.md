# Build the log, borrow only the index

precog should keep its disk storage engine a **purpose-built segment log written with plain `std::fs` buffered `pwrite` + `fdatasync` into pre-zeroed, recycled segment files**, and should not hand its 3-30 KB batches to any embedded database. The project's own benchmark of 13 backends under precog's exact group-commit workload settles this. Recycled, pre-written segments beat today's `O_APPEND` log by **1.08x-1.33x in throughput with lower p99**, and they need no new dependency. Every LSM and B-tree engine lands at **0.31x-0.71x** at 27 KB with 16 producers, and the LSMs show **p99 acks of 32-74 ms** from flush and compaction stalls ([precog benchmark](../results/STORAGE.md)). The only off-the-shelf engine that keeps up is TiKV's raft-engine (0.96x-1.24x). Its read path was weak in the benchmark, though, and its crates.io release predates a 2026 fix that makes `sync()` actually fsync the active log ([raft-engine commits](https://github.com/tikv/raft-engine/commits/master)). io_uring and fallocate-only preallocation gave no meaningful gain. O_DIRECT|O_DSYNC won when latency-bound (1.5x-1.7x) but cut uncached reads by 5-10x. The real weakness of precog's current log is recovery, not write speed: a cold restart replays every segment in **1.4-5.8 s**, against 1-250 ms for engines with persistent indexes. The fix is Kafka/Iggy-style per-segment sparse index files plus a double-buffered checkpoint, with a small embedded KV (redb or LMDB via heed) at most for metadata. The rest of this report sets out the evidence, then a phased build-vs-depend plan and the Linux durability rules the code must follow.

## Pre-zeroed segments win; databases lose 30-70% at 27 KB

The benchmark is the primary evidence because it puts every candidate behind the same front end. P producer threads each append one batch keyed by (log, seq) and block until durable. One writer thread drains the queue into a single `append_group()` that returns only once the whole group is on stable storage. The grid covered 13 backends × {27 KB, 2.7 KB} values × {1, 4, 16} producers, with 2 repetitions of 8 s each, for 156 runs on a 4-vCPU VM with ext4 on virtio ([precog benchmark notes](../research_notes/Rust%20storage%20engine%20for%20precog/benchmark_results.md); harness in `crates/storage-bench`, raw data in `results/storage.jsonl`). Seven conclusions follow from the full grid ([precog benchmark](../results/STORAGE.md)). First, **recycled pre-written segments are the cheapest real win**: +8% to +33% throughput and lower p99 for essentially the same code. Second, **`fallocate()` alone is not a substitute**. It comes in at 0.83x-1.02x, because unwritten extents force a metadata journal commit on each first write. Third, **O_DIRECT|O_DSYNC is fastest when latency-bound and uses the least CPU**: p50 192 µs vs 341 µs. That edge shrinks to 1.08x once groups are large and the device saturates near 300 MB/s, and uncached reads fall to 18-36k gets/s and 1.7 GB/s scans. Fourth, **io_uring gave nothing a single blocking writer lacked** (0.89x-1.20x, with higher CPU at low concurrency), because the flush dominates. Fifth, **raft-engine matches raw-prealloc on writes and reopens in 66-640 ms**, but managed only 10k point gets/s and 308 MB/s scans under the heaviest load. Sixth, **LSMs are fine at 2.7 KB (0.8x-0.9x) and break down at 27 KB**, where they write 3.3-4.3x the user bytes to the device. Key-value separation halves that amplification, but p99 still sits near 33 ms. Seventh, **B-trees are the wrong home for batch data and the right home for an index**. At 2.7 KB with 1 producer they amplify device writes 10-16x (redb 16.0, LMDB 10.8, SQLite 10.2, vs 2.6 for raw-prealloc). Yet LMDB serves 1.1-2.4M point gets/s and redb 0.45-0.67M, and both reopen in about 1-2 ms with no replay.

The caveats bound how far these numbers transfer. The runs are short (8 s), so long-run compaction debt and B-tree growth past about 2 GB are not captured, and retention cost was not measured. Engines ran with near-default settings and compression off. The raw backends' point gets use an in-memory hash index, which flatters them compared with an on-disk sparse index. Most importantly, the VM's flush costs about 120-300 µs. On power-loss-protected NVMe the flush drops to a few µs, which shifts the bottleneck to CPU and filesystem metadata and would likely widen the lead of the lean raw paths and O_DIRECT. *The raw-falloc reopen figure is invalid. The harness re-created its first segment with `truncate` on reopen, which wiped the data. All 12 raw-falloc runs failed the read-back check after reopen. Its write-phase numbers are unaffected, and its recovery cost should match the other raw variants. The bug is fixed in `crates/storage-bench`.

## Why the file's metadata, not the disk, sets the commit cost

The 2.4x gap the project measured earlier is the key to the I/O choice: a 27 KB append plus fdatasync took 297 µs at p50, the same write into a pre-zeroed file 123 µs. `fdatasync` skips metadata "unless that metadata is needed in order to allow a subsequent data retrieval", and a file-size change is the man page's own example of metadata that must be flushed ([fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html)). Every `O_APPEND` write grows i_size and so forces an ext4 journal commit inside the sync. Preallocation with `fallocate` swaps that cost for another. ext4 and XFS create **unwritten** extents, and the first write must convert them. A linux-ext4 benchmark measured O_DSYNC overwrites at about **20.1k IOPS into unwritten extents versus 98.8k into already-written blocks** ([LWN 1005186](https://lwn.net/Articles/1005186/)), and ftrace attributes the time to `ext4_convert_unwritten_extents()` ([linux-ext4 2022](https://lists.openwall.net/linux-ext4/2022/06/17/13)). PostgreSQL arrived at the same answer years ago: `wal_init_zero` fills new WAL segments with real zeros, and `wal_recycle` renames old segments for reuse ([PostgreSQL WAL config](https://www.postgresql.org/docs/current/runtime-config-wal.html)). TiKV added `enable-log-recycle` to raft-engine specifically "to reduce the long tail latency on write workloads" ([TiKV config](https://docs.pingcap.com/tidb/stable/tikv-configuration-file/)). A proposed `FALLOC_FL_WRITE_ZEROES` would let filesystems allocate written extents cheaply ([LWN 1014553](https://lwn.net/Articles/1014553/)), but the notes could not confirm it has merged, so precog should zero-fill on a background thread or recycle sealed files.

O_DIRECT is a real latency lever, but not a durability primitive. It "does not give the guarantees of O_SYNC" and requires buffer, offset and length aligned to the logical block size ([open(2)](https://man7.org/linux/man-pages/man2/open.2.html)). Durability still needs O_DSYNC, `pwritev2(RWF_DSYNC)` ([pwritev2(2)](https://man7.org/linux/man-pages/man2/pwritev2.2.html)) or an fdatasync. The systems that use it, TigerBeetle and Redpanda, also run their own page cache ([TigerBeetle safety](https://docs.tigerbeetle.com/concepts/safety/); [Redpanda autotune](https://www.redpanda.com/blog/autotune-series-part-1-storage)). The benchmark shows why that cache is mandatory: without it, reads from precog's live subscribers would drop from about 140k to 18k gets/s. O_DIRECT also forces a rewrite of the partial tail block on every group. That is a real design cost, and Seastar's output stream cannot flush partial pages at all ([Seastar discussion, secondary](https://hacklines.com/en/editions/287021/click)).

io_uring is the wrong lever for this workload. It can chain a write and an `IORING_FSYNC_DATASYNC` with `IOSQE_IO_LINK` ([io_uring_enter(2)](https://man7.org/linux/man-pages/man2/io_uring_enter.2.html)), but one writer issuing one flush at a time saves only one or two syscalls against a flush of hundreds of µs. The benchmark confirmed this. The operational costs are large. Docker's default seccomp profile blocks `io_uring_setup`/`enter`/`register` ([Docker seccomp](https://docs.docker.com/engine/security/seccomp/)). Google disabled io_uring on ChromeOS and its production servers after about 60% of 2022 kCTF exploit submissions targeted it ([oss-security](https://openwall.com/lists/oss-security/2023/06/17/2)). Linux 6.6 added a sysctl to switch it off host-wide ([kernel sysctl docs](https://docs.kernel.org/admin-guide/sysctl/kernel.html#io-uring-disabled)). Completions are also unordered: Apache Iggy found that batched io_uring writes completing out of order corrupted on-disk state after a crash, and fixed it with link chaining ([Iggy blog](https://iggy.apache.org/blogs/2026/02/27/thread-per-core-io_uring/)). The crate landscape is uneven. The low-level `io-uring` crate (0.7.16, Nov 2026) and `compio` (0.19.2, Iggy's runtime) are active, while `tokio-uring` (last release May 2024), `glommio` (Mar 2024, "pretty much unmaintained" per Iggy) and `monoio` (Aug 2024) are stale ([crates.io io-uring](https://crates.io/crates/io-uring); [compio](https://crates.io/crates/compio); [Iggy blog](https://iggy.apache.org/blogs/2026/02/27/thread-per-core-io_uring/)). Iggy did gain from its move to compio, from 843 to 992 MB/s with p99 falling from 19.7 to 13.0 ms in fsync mode. That gain came from a thread-per-core rewrite of a whole server, though, not from a single WAL writer.

Two smaller primitives round out the toolbox. `sync_file_range` writes no metadata and flushes no device cache. Its man page calls it "extremely dangerous", so it can at most smooth writeback on sealed segments ([sync_file_range(2)](https://man7.org/linux/man-pages/man2/sync_file_range.2.html)). mmap is a poor write path, because the kernel controls writeback order and errors arrive as SIGBUS rather than return codes ([Crotty, Leis & Pavlo, CIDR 2022](https://db.cs.cmu.edu/mmap-cidr2022/)). It is acceptable for reading immutable sealed segments and their index files. The syscalls `std` lacks (fallocate, `pwritev2`, `posix_fadvise`, `statx` alignment) come from `rustix` 1.1.6 or `nix` 0.32 ([crates.io rustix](https://crates.io/crates/rustix); [nix](https://crates.io/crates/nix)).

## Embedded engines belong behind the index, never under the data

The engine survey explains the benchmark's split. Only purpose-built logs and LSMs with key-value separation avoid rewriting 3-30 KB values. RocksDB's BlobDB keeps large values out of compaction ([BlobDB wiki](https://github.com/facebook/rocksdb/wiki/BlobDB)), and fjall 3 adopted "a scheme more similar to RocksDB's BlobDB" ([Fjall 3.0](https://fjall-rs.github.io/post/fjall-3/)). Even then the WAL writes each value once and the blob file writes it again, which matches the roughly 2.0x device amplification measured. Retention exposes the same mismatch. RocksDB FIFO compaction can drop whole SSTs by size or TTL, but the wiki warns it "can drop data without notifying users" and that many L0 files slow queries ([FIFO wiki](https://github.com/facebook/rocksdb/wiki/FIFO-compaction-style)). fjall lists O(1) range deletion as missing ([Fjall 3.0](https://fjall-rs.github.io/post/fjall-3/)). redb's own removals benchmark is the slowest of five engines ([redb README](https://github.com/cberner/redb)). Immutable segment files reduce retention to `unlink`. PingCAP took the same path for production reasons: it moved TiKV's Raft logs out of RocksDB into raft-engine, cutting write I/O by 25-40%, and kept user data in RocksDB ([TiKV 6.1 notes](https://tikv.org/docs/6.1/new-features/overview/); [PingCAP write-up](https://pingcap.com/?p=9415)).

Project health narrows the field further. The table summarises the candidates as of 17 Nov 2026 ([embedded engine notes](../research_notes/Rust%20storage%20engine%20for%20precog/embedded_engines.md)):

The hybrid's real risk is two durability domains. If the index KV must commit in the same group as the data, every group pays a second fsync. The better design makes the index **derivable**: sealed segments carry their own index files, and the active segment's index is rebuilt from a short tail scan. The KV then holds only small metadata such as the segment catalog, writer epochs and high-water marks. At that write rate any of redb, heed or SQLite suffices, and redb's bug history matters less because the KV is never the sole copy of acknowledged data.

## Kafka, BookKeeper and Iggy already drew precog's layout

Production systems fall into two families ([production designs notes](../research_notes/Rust%20storage%20engine%20for%20precog/production_designs.md)). In "log equals data", Kafka and Iggy keep per-partition segment files with a sparse index. Kafka defaults to one index entry per 4 KiB (`log.index.interval.bytes` = 4096) and binary-searches an in-memory range per file ([Kafka ServerLogConfigs](https://github.com/apache/kafka/blob/trunk/server-common/src/main/java/org/apache/kafka/server/config/ServerLogConfigs.java); [Kafka log.md](https://github.com/apache/kafka/blob/trunk/docs/implementation/log.md)). Iggy writes one 24-byte `{offset, timestamp, position}` entry per flush chunk, serving as both offset and time index, with 1 GiB segments as a soft cap ([iggy_index.rs](https://github.com/apache/iggy/blob/master/core/partitions/src/iggy_index.rs); [Iggy config](https://github.com/apache/iggy/blob/master/core/server/config.toml)). In "shared journal plus separate data", BookKeeper, raft-engine and TigerBeetle have one sequential journal absorb group commit from all writers. BookKeeper waits up to 2 ms to group journal force-writes and fsyncs before ack by default ([BookKeeper config](https://bookkeeper.apache.org/docs/reference/config)). raft-engine's first queued writer becomes leader, writes the group and calls `fdatasync()` ([raft-engine README](https://github.com/tikv/raft-engine)). precog's single node-wide WAL with cross-writer group commit belongs to the second family, and it inherits that family's known problem. Interleaved data from many streams with different retention punches holes in shared files. BookKeeper solves this by compacting entry logs below 20% live data. raft-engine solves it with hole compaction and a callback naming the groups that block GC.

The fsync policy split is instructive. Kafka disables application fsync entirely and relies on replication, claiming per-write fsync costs "two to three orders of magnitude" ([Kafka design.md](https://github.com/apache/kafka/blob/trunk/docs/design/design.md)). Redpanda fsyncs before ack by default and calls Kafka's approach unsafe under correlated failures ([Redpanda fsync blog](https://www.redpanda.com/blog/why-fsync-is-needed-for-data-safety-in-kafka-or-non-byzantine-protocols)). It also offers opt-in write caching, which cut EBS p99 from about 113 ms to 8.5 ms ([Redpanda write caching](https://www.redpanda.com/blog/write-caching-performance-benchmark)). Iggy makes the choice per topic: "replicated" adds no barrier, "persisted" requires stable storage at a quorum. It adds `wal_group_commit_delay_micros`, a bounded wait that is skipped when arrivals are sparse ([Iggy config](https://github.com/apache/iggy/blob/master/core/server/config.toml)). precog's fdatasync-before-ack sits with Redpanda and BookKeeper. Iggy's adaptive delay is a cheap knob worth copying for small-batch traffic on fast devices.

Recovery practice converges on one rule: **persist a recovery point and scan only what follows it**. Kafka checkpoints a recovery point every 60 s and CRC-validates only the newest segment, truncating at the first invalid batch ([Kafka log.md](https://github.com/apache/kafka/blob/trunk/docs/implementation/log.md)). TigerBeetle replays its WAL from the last superblock checkpoint ([TigerBeetle safety](https://docs.tigerbeetle.com/concepts/safety/)). Iggy publishes a two-slot checksummed WAL frontier. It gave the frontier a new magic number so that older binaries refuse to open it rather than truncate acknowledged records to a stale length ([partition_journal.rs](https://github.com/apache/iggy/blob/master/core/journal/src/partition_journal.rs)). Iggy also treats an on-disk index entry as proof that the bytes it names were already fdatasynced, and it refuses blind truncation of interior damage: "Interior damage or valid records after a damaged range require refusal or repair" ([segment_recovery.rs](https://github.com/apache/iggy/blob/master/core/partitions/src/segment_recovery.rs); [Iggy config](https://github.com/apache/iggy/blob/master/core/server/config.toml)). On reads, Kafka relies on the page cache, so caught-up consumers cause "no read activity on the disks whatsoever" ([Kafka design.md](https://github.com/apache/kafka/blob/trunk/docs/design/design.md)). Iggy also stays buffered, layering serving caches "on top of page cache". That supports keeping precog buffered and serving live subscribers from an in-process ring of recent batches.

## The recommended engine, built in three phases

The design that follows from the evidence has one WAL writer thread on blocking `std::fs`, three file kinds on disk, and one optional small KV. The active WAL segment is a pre-zeroed or recycled file of fixed size (256 MiB-1 GiB, a hard bound so peer-transfer buffers can be sized from it, a lesson from Iggy's livelock). The writer drains the queue, `pwrite`s the group at a tracked offset, calls `File::sync_data`, then wakes every waiter. Each batch is framed as `[magic | segment_generation | lsn | len | crc32c] payload` together with its (stream, writer, epoch, first_seq) identity. The generation field lets recovery reject stale records from a recycled file's previous life, as RocksDB's recyclable format does ([RocksDB WAL-Performance wiki](https://github.com/facebook/rocksdb/wiki/WAL-Performance)). At roll, the segment is sealed with a sidecar sparse index file sorted two ways: by (log, writer seq) for random reads and by local position for tailing. Each index holds about one entry per 4 KiB-64 KiB or per batch, with a footer checksum. A two-slot checksummed checkpoint records the WAL position up to which all sealed segments and indexes are durable. Retention unlinks whole sealed segments by time or size, then fsyncs the directory. Because precog's WAL interleaves streams, segments with mixed retention must either wait for their longest-lived stream or have survivors copied forward. Decide that policy explicitly rather than inherit BookKeeper-style compaction by accident.

| phase | build | depend on | exit criterion |
|---|---|---|---|
| 0: cheap wins now | Recycled, pre-zeroed segments with a spare ready off the commit path; generation-stamped CRC-32C framing; fatal-on-fsync-error; directory fsync on create/rename/unlink | `std::fs`, `rustix` (fallocate/fadvise), `crc32c` | Reproduce the +8% to +33% and lower p99 from the benchmark |
| 1: fast recovery | Per-segment sparse index sidecars, two-slot checkpoint, tail-only replay; torn-tail truncate vs interior-corruption fence-and-repair-from-peers; in-memory ring for live tails; `posix_fadvise(DONTNEED)` on cold sealed segments | Optional `heed` or `redb` for segment catalog, writer epochs and high-water marks only, always rebuildable from segments | Cold reopen bounded by one segment's scan (≪1 s), not the 1.4-5.8 s measured today |
| 2: device-specific tuning | Optional O_DIRECT\|O_DSYNC writer with an owned aligned buffer and block cache, behind a flag, for PLP NVMe or latency-bound nodes; Iggy-style bounded group-commit delay; optional `io-uring` 0.7 writer with a pwrite fallback for EPERM/ENOSYS | `io-uring` (only if re-benchmarking on target hardware shows a gain) | Benchmark on production-class hardware beats Phase 1 by a margin that justifies the cache code |

raft-engine is the one serious alternative to building Phase 0-1, since it already provides group commit, recycling and file purge. It loses on three counts: its reads are weak under load in precog's benchmark, it requires a git pin to get correct `sync()` semantics, and its per-group memtable model maps poorly onto precog's (stream, writer, epoch) identity. It remains a useful code reference for the leader-writer queue.

The gotchas below are each non-negotiable, and most have bitten mature systems.

| gotcha | rule for precog | source |
|---|---|---|
| fsync errors are reported once; pages are marked clean | On any `sync_data` error, fail the whole group, never retry-and-ack, crash or fence the node, recover from disk and peers | [PostgreSQL Fsync Errors](https://wiki.postgresql.org/wiki/Fsync_Errors); [Rebello et al., ATC'20](https://www.usenix.org/system/files/atc20-rebello.pdf) |
| Appends grow i_size; fallocate leaves unwritten extents | Write into pre-written zeros or recycled files only; never `O_APPEND` on the commit path | [fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html); [LWN 1005186](https://lwn.net/Articles/1005186/) |
| Recycled files hold stale valid-looking records | Stamp a segment generation in every frame; stop replay on mismatch | [RocksDB recycling commit](https://git.nextgraph.org/NextGraph/rocksdb/commit/3316d29221f12596663b9ed28a153328674b3de9) |
| File fsync does not persist the directory entry | fsync the directory fd after create, rename and unlink, before acking into a new segment | [fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html); [ALICE, OSDI'14](https://pages.cs.wisc.edu/~remzi/Classes/739/Fall2016/Papers/alice-osdi14.pdf) |
| Multi-sector writes tear; inode size can land before data | CRC every batch; truncate a torn tail; treat valid records after a bad one as media corruption and repair from peers | [Kafka log.md](https://github.com/apache/kafka/blob/trunk/docs/implementation/log.md); [Iggy config](https://github.com/apache/iggy/blob/master/core/server/config.toml) |
| O_DIRECT is not durable; alignment rules vary | Pair with O_DSYNC or fdatasync; get alignment from `statx(STATX_DIOALIGN)` | [open(2)](https://man7.org/linux/man-pages/man2/open.2.html); [statx(2)](https://man7.org/linux/man-pages/man2/statx.2.html) |
| io_uring completes out of order and may be blocked | Link WRITE→FSYNC; keep a blocking fallback | [Iggy blog](https://iggy.apache.org/blogs/2026/02/27/thread-per-core-io_uring/); [Docker seccomp](https://docs.docker.com/engine/security/seccomp/) |
| `sync_file_range` and mmap writes are not durability | Never on the commit path | [sync_file_range(2)](https://man7.org/linux/man-pages/man2/sync_file_range.2.html); [CIDR 2022](https://db.cs.cmu.edu/mmap-cidr2022/) |
| Format changes let old binaries truncate acked data | Version magic so old builds refuse to open, never "repair" | [partition_journal.rs](https://github.com/apache/iggy/blob/master/core/journal/src/partition_journal.rs) |
| Flush cost varies 1,000x by device | Benchmark on target hardware: PLP NVMe 0.7-12 µs, consumer NVMe 0.45-3 ms, Hyperdisk fdatasync 46 µs vs fsync 738 µs | [Small Datum 2026](https://smalldatum.blogspot.com/2026/01/ssds-power-loss-protection-and-fsync.html) |
| A single node's flush may lie | Count durability as K-of-N fdatasyncs across the mesh, not one disk | [TigerBeetle safety](https://docs.tigerbeetle.com/concepts/safety/) |

## Conclusion

The question "which Rust storage library?" turns out to have a narrow answer: none for the data path, and something small and boring for metadata. Every engine adds a second copy of the data (WAL plus blob or page), an amplification factor, or a stall source to a workload that is already the ideal shape for a log: immutable, append-only, group-committed and retained by age. precog's measurable gaps are a missing recovery point and the i_size and extent metadata that `O_APPEND` drags into every sync. Neither is fixed by adopting a database, and both are fixed in a few hundred lines of code on top of `std::fs`.

The bigger open risk sits outside this benchmark's reach. The VM's 120-300 µs flush hides how lopsided the trade-offs become on real hardware. On PLP NVMe, filesystem metadata and CPU dominate and O_DIRECT's case strengthens. On network disks, fsync versus fdatasync alone is a 16x gap. The interleaved single-WAL layout also creates a retention-compaction problem that the 8-second runs never exercised. The next benchmarks precog runs should therefore be on its production device class and over hours, with mixed-retention streams. Those results, not library choice, will decide whether Phase 2 is worth building.
