# Precog against s2-lite, through S2's own REST API (2026-11-19)

`bench/s2/suite.sh` on one 4-vCPU VM (2.1 GHz Xeon, ext4 on a virtio disk, 15 GiB RAM). Every
server runs in a container on one Docker network. The driver (`crates/s2-lab` `s2bench`) runs on
the host and speaks S2's REST v1 API identically to both systems: unary JSON appends over
HTTP/1.1 keep-alive, and SSE for reads.

## Systems

| system | what acknowledges an append |
|---|---|
| s2lite-mem | s2-lite 0.47.0 (`ghcr.io/s2-streamstore/s2`), in memory: no durability |
| s2lite-disk | s2-lite, SlateDB on local disk (`--local-root`), its default 5 ms flush |
| s2lite-silo | s2-lite, SlateDB on S3-compatible Silo (`pgsty/silo`, a MinIO fork), its default 50 ms S3 flush |
| s2lite-silo5 | the same with `SL8_FLUSH_INTERVAL=5ms` |
| precog1 | POC gateway + 1 Precog node: the batch is fsynced on the node |
| precog3 | POC gateway + 3 Precog nodes: fsynced on 2 of 3 (the third copy follows) |
| gw-s3 | POC gateway, S3 group-commit WAL on Silo: acked after the PUT of the object holding the batch |
| gw-none | POC gateway acking without storing: the HTTP, JSON and sequencing cost alone |

The gateway (`crates/s2-lab/src/bin/gateway.rs`) maps an S2 stream onto one Precog writer log
whose sequence numbers are the stream's seq_nums. A per-stream task owns a
`precog_lab::s2::Sequencer` and pipelines batches to the mesh, acknowledging them in order.

## Workloads

- **A**: closed loop. 4 streams × 4 writers, one append in flight per writer, 100 records × 256 B
  per append, one SSE tail reader per stream. 5 s warm-up, 20 s measured.
- **B**: paced at 10,000 records/s. 4 streams × 2 writers, 10 records per append, one SSE reader per
  stream. A closed-loop writer cannot exceed one append per round trip, so s2lite-silo reaches
  only 1,560 records/s here.
- **Probes**, after the load on an idle system, 50 or 30 trials each:
  - a 1-record append;
  - check-tail;
  - a unary read of 100 records from 1000 behind the tail (time to the first byte, and to the
    full body);
  - an SSE read from `tail_offset=10` (time to the first `batch` event).

## Metrics

- **Server CPU:** the containers' cgroup CPU time over the measured window, divided by records
  acknowledged. It excludes Silo, which is reported separately as object-store CPU.
- **RSS:** peak `total_rss` sampled every second.
- **Disk:** what the data directories hold. Precog preallocates 256 MiB segments, so its disk
  figure is the allocation, not the data.

## Run order

Systems alternate inside each round. The first suite completed every s2-lite run, but all
Precog-side runs after the first failed: Docker Hub answered the per-run base-image lookup with
429. A second suite ran the Precog systems interleaved with s2lite-disk, s2lite-silo and
s2lite-silo5 as controls. Those three therefore have 6 runs, the others 3 or 4. Every table gives
medians.

## Million streams (`bench/s2/streams.sh`, `results/s2-streams.jsonl`)

Each stream is created by one append of a 64-byte record, 64 requests in flight. After a
`docker stop` (graceful), the server is started again. Restart time runs until it answers: for
s2-lite, a read of the last stream; for Precog, the node accepting connections.

| system | streams | create rate | RSS | per stream | RSS after restart | restart | disk |
|---|---:|---:|---:|---:|---:|---:|---:|
| Precog node, native protocol, 1 copy | 1,000,000 | 41,966/s | 3,778 MiB | ~3.9 KB | 3,564 MiB | 8.9 s | 512 MiB (one preallocated segment) |
| s2-lite, local disk | 1,000,000 | 2,830/s | 2,112 MiB | ~2.2 KB | **44.5 MiB** | 1.3 s | 1,795 MiB |
| POC gateway + Precog node | 500,000 | 6,912/s | 6,186 MiB | ~13 KB (gateway ~8.8 KB) | node only: 1,782 MiB | node only: 3.5 s | 512 MiB |

- **Precog keeps every stream resident on every node.** Each writer log has its batch map,
  frontier and per-stream order, and a restart rebuilds all of them.
- **s2-lite loads streams lazily.** A dormant stream costs nothing until it is touched. That is the
  property behind S2's "unlimited streams".
- **The gateway's streamer per stream** costs ~8.8 KB, after shrinking its channels from 1024 to
  64/16 slots (it was 45 KB at 1024). A product evicts idle streamers.

## What the numbers say

1. **Write latency is set by where durability lives, not by the API.** Through the same JSON client:

   | workload | Precog 2-of-3 | s2-lite on Silo | s2-lite on Silo, 5 ms flush | s2-lite, local disk |
   |---|---:|---:|---:|---:|
   | B (10k rec/s), append p50 / p99 | 1.98 / 5.0 ms | 51.2 / 54.4 ms | 6.24 / 12.1 ms | 5.86 / 10.1 ms |
   | idle 1-record append, p50 | 0.97 ms | 51.3 ms | 6.05 ms | — |

   S2's cloud SLOs are 40 ms (Express) and 400 ms (Standard).
2. **Throughput and CPU** (workload A, closed loop):

   | system | records/s | server CPU per record |
   |---|---:|---:|
   | precog3 (durable on 2 nodes) | 229k | 6.9 µs |
   | precog1 | 389k | 3.8 µs |
   | s2lite-silo | 31k | 10.2 µs, plus 6.0 µs in Silo |
   | s2lite-silo5 | 99k | 11.7 µs, plus 6.4 µs in Silo |
   | s2lite-disk | 135k | 13.2 µs |

   The gateway alone costs 1.75 µs per record (gw-none, 834k records/s).
3. **An object-storage group commit in Precog's gateway** acks at 4.5 ms p50 (B) and 2.25 ms
   (idle) on loopback Silo. That is Silo's PUT time. On real S3 Standard the same design pays
   S3's PUT latency, tens of ms. A PUT per commit also costs money (see the economics report).
4. **Reads are equal and fast on both.**

   | probe | Precog 3-node | s2-lite |
   |---|---:|---:|
   | check-tail | 0.27–0.35 ms | 0.36–0.48 ms |
   | unary read time to first byte | 0.8–1.0 ms | 0.4–0.9 ms |
   | SSE first batch | 0.31–0.39 ms | 0.28–0.96 ms |

   s2-lite serves recent data from memory; the gateway reads through the mesh's `ReadCursor`.
5. **End-to-end tail latency** (append to SSE delivery) follows the append latency. The p99 in
   workload A on every gateway system (35–56 ms) comes from one SSE reader per stream on a
   saturated 4-vCPU host.

## Caveats

- **One VM, 4 vCPUs, shared by everything:** the servers, Silo, the driver and three Precog
  nodes. Precog's 3 nodes share one disk, so "2 of 3 durable" is not independent hardware.
  Silo on loopback has none of S3's latency. Identical runs on this VM vary by up to ~20%.
- **The comparison is narrow.** s2-lite is a single-node emulator of a cloud service. The cloud's
  latency, durability (multi-AZ object storage) and elasticity are not reproduced here, and
  neither is S2S (HTTP/2 binary sessions), which the official SDKs use for pipelined appends.
  Unary JSON appends penalize s2-lite's 50 ms S3 flush (one append in flight per writer) more
  than they would a session.
- **The POC gateway is not product code:**
  - it poisons a stream on any failed write;
  - it serves reads only from the mesh (not in gw-s3 or gw-none, whose read probes are
    meaningless);
  - it has no auth, no trim, no basins API and no S2S.
- **The disk column** counts Precog's preallocated segments and SlateDB's files. Neither is the
  stored data size.
- **Not measured:**
  - S3-backed s2-lite against real S3 or S3 Express;
  - multi-machine latency;
  - failover of a stream owner (only the zombie-owner guard is tested:
    `crates/lab/tests/s2_zombie.rs`).
