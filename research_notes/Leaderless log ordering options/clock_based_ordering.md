## Q1. Can node-assigned HLC plus all-node watermarks give every reader the same total order without consensus? What breaks it?

### Takeaway
Yes, if the node set is fixed and every node keeps sending watermarks. Stamping (ts, node_id, seq) is deterministic, so all readers that deliver only below min(watermarks over all nodes) deliver the same total order with no consensus. This is how Flink watermarks, CockroachDB closed timestamps and TiKV resolved ts all work. Its weak point is liveness: one silent node stalls everyone. Unstalling safely means deciding that the node is dead or idle *and* agreeing which of its entries below the cut are in. That decision is agreement on membership/cut, i.e. consensus. Every production system we found puts that decision in a consensus-backed component (Raft leaseholder/epochs in CockroachDB, PD/Raft in TiKV). Flink's workaround (`withIdleness`) gives up correctness: data from the "idle" input that arrives later is late.

### Cited Findings
- **HLC mechanism and guarantees.** HLC (Kulkarni, Demirbas et al., "Logical Physical Clocks and Consistent Snapshots in Globally Distributed Databases") keeps a timestamp l close to physical time pt. If e happened-before f, the HLC of e is less than the HLC of f. It fits in the 64-bit NTP timestamp format, and Corollary 1 proves |l.f − pt.f| ≤ ε, where ε is the clock-sync bound. The logical counter c stays bounded (the paper stress-tests it at 1 event/ms with 10–100 ms drift). It is "masking tolerant to NTP kinks." — [HLC tech report, Univ. at Buffalo 2014-04](https://cse.buffalo.edu/tech-reports/2014-04.pdf)
- HLC captures only happened-before. Two events with no causal link are ordered by physical time to within ε, not exactly. (This follows from the |l − pt| ≤ ε bound in the paper.) — [HLC tech report](https://cse.buffalo.edu/tech-reports/2014-04.pdf)
- **Min-watermark stalls (Flink).** When there are parallel inputs, the combined watermark is the minimum. An idle input "holds back the watermark because it is computed as the minimum over all the different parallel watermarks." Two-input operators also take the min. The workaround is `withIdleness(Duration.ofMinutes(1))`, which marks the input idle and excludes it. Watermark alignment (`withWatermarkAlignment(group, maxDrift, updateInterval)`) stops fast sources from running ahead and limits buffering. Bounded out-of-orderness emits max-seen minus the bound minus 1 ms. — [Flink docs: Generating Watermarks](https://nightlies.apache.org/flink/flink-docs-stable/docs/dev/datastream/event-time/generating_watermarks/)
- **Closed timestamps (CockroachDB)** are a per-range promise that "no new writes can ever be introduced at or below that timestamp." The leaseholder advances the closed timestamp, which trails current time by a target interval, and notifies followers. A write that arrives at or below the closed timestamp has its timestamp pushed up, which can cause a retry. Any replica can serve reads at or below the closed timestamp. — [CockroachDB docs: Follower Reads](https://docs.cockroachlabs.com/docs/stable/follower-reads)
  - This is the key trick for precog: a late write is not dropped and does not break order. It is **re-stamped above the watermark**. The node that issued the watermark enforces that, so the promise is local to that node. The node is a Raft leaseholder in CRDB.
- Idle ranges get no Raft commands to carry closed timestamps. A side transport (`kv.closed_timestamp.side_transport_interval`, default 200 ms) advances them. — [CockroachDB v25.1 advanced changefeed config](https://www.cockroachlabs.com/docs/v25.1/advanced-changefeed-configuration); [v23.1](https://www.cockroachlabs.com/docs/v23.1/advanced-changefeed-configuration)
- **TiKV resolved ts.** TiKV advances resolved-ts per region every `resolved-ts.advance-ts-interval` (default 1s, dynamic, added in TiDB 5.1). — [TiDB 5.1 release notes](https://docs.pingcap.com/tidb/dev/release-5.1.0)
- **Stall symptoms in practice.** TiCDC alert rules flag a changefeed whose resolved ts is more than 5 minutes behind, and a TiKV min resolved ts that has not advanced for 1 minute. — [TiCDC alert rules (archive v7.3)](https://docs-archive.pingcap.com/tidb/v7.3/ticdc-alert-rules/)
  - Community threads show changefeed checkpoints stopping when TiKV nodes lag on resolved ts (one case after a TiDB OOM). — [ask.pingcap.com 8564](https://ask.pingcap.com/t/ticdc-latency-is-very-high-and-the-background-keeps-logging-the-resolvedts-is-fallen-back-in-kvclient/8564); [ask.pingcap.com 6857](https://ask.pingcap.com/t/the-min-resolved-ts-of-ticdc-has-a-long-delay/6857)
  - Resolved ts can get stuck during changefeed init under high rates (tiflow #11066). — [GitHub tiflow #11066](https://WWW.GITHUB.COM/pingcap/tiflow/issues/11066)
  - PingCAP's tuning docs say TiKV can fail to advance resolved ts in time under heavy write load. — [TiCDC performance tuning](https://docs.pingcap.com/tidb/dev/ticdc-performance-tuning-methods/)
- **Ordered output from TiCDC.** TiCDC's Log Service pulls row changes, stores them on local disk, merges and sorts them, then pushes them downstream. Storage-sink consumers must themselves sort DML by `commit-ts` across subtasks. — [TiCDC architecture](https://docs.pingcap.com/tidb/stable/ticdc-architecture/)
- **Self-fencing on clock offset (CockroachDB).** If a node exceeds the configured maximum offset, "it self-terminates." — [CockroachDB blog: Living without atomic clocks](https://www.cockroachlabs.com/blog/living-without-atomic-clocks/)
- **Tempo (EuroSys'21)** is the closest leaderless analogue to "timestamp + stability watermark." Each command gets a timestamp and executes only once that timestamp is *stable* (all lower-timestamp commands are known). Both timestamping and stability detection are decentralized, with no leader. Tempo is a full SMR protocol with quorums, not quorum-free. — [Enes, Baquero, Gotsman, Sutra, arXiv:2104.01142](https://arxiv.org/abs/2104.01142)

### Inferences
- **Agreement in the fault-free, fixed-membership case.** Suppose each node N stamps a batch with t = HLC_N and sends a watermark W_N with the promise "I will never stamp ≤ W_N again; anything that arrives late gets stamped > W_N." Then a reader that delivers entries with t ≤ min_N(W_N), sorted by (t, node, seq), delivers a prefix that is the same for every reader. This needs no consensus. Completeness comes from each node's local promise plus the reader holding all of that node's entries ≤ W_N.
- **Durability of a node's entries.** Precog acks at 2 of 3 copies, so a reader may get node N's entries from a peer replica. The watermark must then cover *durable* entries only: N should send W_N only after the entries ≤ W_N are 2/3-durable. Otherwise, if N dies after sending W_N, a reader could deliver past an entry that only N held, and that entry could later reappear and break agreement.
- **Dead/slow node.** min(W) stalls. Removing N from the min means the survivors must agree on (a) that N is out, and (b) the final W_N and N's complete set of entries ≤ final W_N. A reader that removes N on its own timeout, while another waits, can diverge. This is a consensus problem. One option keeps it off the data path: a Raft-replicated membership/epoch service that seals N's epoch at a final watermark. That is CRDB's pattern, with leases and epochs in a consensus layer. It is also essentially Scalog's "Raft-committed cut," applied only on failure.
- **Membership change** needs the same agreement: a new node can contribute only from a watermark that all readers agree it starts at.
- **Partition.** If N is partitioned from readers but alive and accepting appends, delivery stalls everywhere until N is fenced. Fencing requires N to learn it is out (lease or epoch), or the protocol risks split-brain entries stamped below the sealed watermark. CRDB's lease and self-terminate rules are examples of this kind of fencing.

### Gaps
- MillWheel's low-watermark design and Timely/Materialize frontiers (progress tracking over pointstamps) were not fetched. From training knowledge (unverified here), MillWheel computes low watermarks centrally, and Timely frontiers rely on a fixed set of workers.
- No source was found that analyzes "HLC + min-watermark across all nodes" as a standalone ordered-broadcast protocol with node failure.

## Q2. What added delivery latency do these schemes report?

### Takeaway
The delivery delay is roughly the watermark/closed-timestamp lag plus the watermark propagation interval. Production defaults are deliberately large: CRDB targets about 3 s with a 200 ms side transport and emits rangefeed checkpoints every 3 s; TiKV advances resolved ts every 1 s. Nothing forces them that high. The floor is roughly one network RTT plus durability time (group commit) plus the watermark send interval, plus ε if you want real-time order. Spanner's commit wait is about 2ε, roughly 5 ms historically. With PTP-class clocks (AWS under 40 µs, Meta about 0.4–0.7 µs WOU), the ε term becomes negligible next to network RTT.

### Cited Findings
- CRDB `kv.closed_timestamp.target_duration` defaults to 3s (it was 30s in v2.1). `side_transport_interval` defaults to 200ms. `kv.rangefeed.closed_timestamp_refresh_interval` emits closed-timestamp events on rangefeeds every 3s. — [CRDB v25.1 changefeed config](https://www.cockroachlabs.com/docs/v25.1/advanced-changefeed-configuration); [CRDB v2.1 cluster settings](https://www.cockroachlabs.com/docs/v2.1/cluster-settings); [CRDB v23.1 cluster settings](https://cockroachlabs.com/docs/v23.1/cluster-settings)
- CRDB exact-staleness follower reads should tolerate data "at least 4.2 seconds in the past." — [CRDB Follower Reads](https://docs.cockroachlabs.com/docs/stable/follower-reads)
- TiKV resolved-ts advance interval defaults to 1s. — [TiDB 5.1 release notes](https://docs.pingcap.com/tidb/dev/release-5.1.0)
- TiCDC's classic architecture polled tasks every 50 ms. The new architecture is event-driven. — [TiCDC architecture](https://docs.pingcap.com/tidb/stable/ticdc-architecture/)
- **Spanner commit wait (reported):** "From the 1-replica experiments, commit wait is about 5ms, and Paxos latency is about 9ms." — [Spanner OSDI 2012](https://static.googleusercontent.com/media/research.google.com/en//archive/spanner-osdi2012.pdf)
- Accord's goal is "one wide area round-trip for all transactions under normal conditions." The CEP page states this as a goal and does not report a measurement. — [CEP-15](https://cwiki.apache.org/confluence/spaces/CASSANDRA/pages/188744725/CEP-15+General+Purpose+Transactions)
- Accord's reorder buffer holds proposals for max clock skew + longest point-to-point latency − coordinator-to-replica latency. — [CEP-15](https://cwiki.apache.org/confluence/spaces/CASSANDRA/pages/188744725/CEP-15+General+Purpose+Transactions)
- Meta reports a "roughly 100x performance difference" for commit-wait reads between state-of-the-art NTP and early PTP. — [Meta Engineering: PTP at Meta (Nov 2022)](https://engineering.fb.com/2022/11/21/production-engineering/precision-time-protocol-at-meta/)

### Inferences (estimates, not reported)
- **Estimated precog delivery latency** for a 3-node single-region mesh: max over nodes of (time from append to 2/3 durable + watermark interval + one-way propagation to the reader). With a 1–10 ms watermark tick and same-AZ/cross-AZ RTTs of about 0.1–2 ms, end-to-end ordered-delivery latency would be on the order of 2–15 ms. These are estimates. The *slowest* node sets the pace (min-watermark), so tail latency is governed by the worst node's group-commit and GC pauses.
- **Idle nodes.** Watermarks must be sent periodically even when a node is idle (CRDB's side transport). Otherwise idle nodes stall delivery.

### Gaps
- No reported end-to-end latency figures were found for CRDB changefeed `resolved` messages or Spanner change streams; those docs were not fetched.
- Latency numbers for EPaxos, Atlas, Caesar and Janus were not fetched.

## Q3. Does the order respect real time across writers (A acked before B sent ⇒ A before B)? Under what clock bound?

### Takeaway
Only with bounded clock error plus a wait. HLC by itself guarantees order only for causally linked events. Two independent producers whose interaction happens outside the system (A's ack is seen by a client, who then makes B send) can be reversed by up to ε. Spanner fixes this with commit wait: A is not acked until TT.after(s_A), so any later B gets a higher stamp. CockroachDB settles for serializability and explicitly allows "causal reverse" across disjoint keys. For precog, the equivalent rule is: ack A only when the receiving node's clock is past t_A + ε. Then any append received later, at any node, gets t > t_A, provided every node's clock error is ≤ ε. The cost is ε of extra ack latency.

### Cited Findings
- **Spanner commit wait.** The coordinator ensures clients cannot see data committed by Ti until TT.after(s_i) is true, so s_i is less than Ti's absolute commit time. This yields external consistency. — [Spanner OSDI 2012](https://static.googleusercontent.com/media/research.google.com/en//archive/spanner-osdi2012.pdf)
- **Spanner ε in 2012.** It was "typically a sawtooth function of time, varying from about 1 to 7 ms over each poll interval" and is "4 ms most of the time." The sawtooth contributes 0–6 ms and communication delay to the time masters about 1 ms. Excursions occur under failures. — [Spanner OSDI 2012](https://static.googleusercontent.com/media/research.google.com/en//archive/spanner-osdi2012.pdf)
- **CockroachDB uncertainty intervals.** CRDB stamps with the local clock and gives each transaction an uncertainty window up to the cluster's max offset. A read that finds a value inside the window restarts above it, at most once per node, and the window shrinks on each restart. CRDB claims serializability, not linearizability. "Causal reverse" can occur for causally related transactions on disjoint keys. Causality tokens only help within one causal chain. With NTP, offsets are typically 100–250 ms. — [CRDB blog: Living without atomic clocks](https://www.cockroachlabs.com/blog/living-without-atomic-clocks/)
  - The 500 ms default `--max-offset` was not confirmed in a fetched page this session. It is widely documented in CRDB docs, but that is training knowledge, unverified here.
- **HLC real-time bound.** |l − pt| ≤ ε. HLC orders causally related events exactly and unrelated events only to within ε. — [HLC tech report](https://cse.buffalo.edu/tech-reports/2014-04.pdf)
- **Clock-error figures on commodity cloud and datacenter hardware:**
  - **AWS:** typical clock error bound under 100 µs over NTP and under 40 µs over the Nitro PTP hardware clock (PHC). The goal is "low double-digit microsecond" accuracy. A sample PHC reading was +18 ns, ±5.03 µs. ClockBound is an open-source daemon and library that reports a confidence interval. The PHC's own error bound must be added from sysfs because chrony underestimates it. AWS names distributed databases and cross-instance/AZ/Region event ordering as use cases. — [AWS Compute Blog: microsecond-accurate clocks on EC2](https://aws.amazon.com/blogs/compute/its-about-time-microsecond-accurate-clocks-on-amazon-ec2-instances/)
  - **Meta PTP:** it targets nanosecond-level sync. Measured end-to-end error is about 92 ns (Calnex). The window of uncertainty is about 436 ns at more than 99.9999% confidence, and a sample `fbclock` WOU reads 694 ns. The WOU grows during holdover. Meta uses it for commit-wait reads (wait until replica ≥ read ts + WOU) to preserve linearizability. — [Meta Engineering, 2022-11-21](https://engineering.fb.com/2022/11/21/production-engineering/precision-time-protocol-at-meta/)
  - **Huygens (NSDI'18):** a software-only system on standard hardware that syncs "to within 100 nanoseconds," and "a few 10s of nanoseconds under varying loads." It needs no special network hardware. Clock frequency discrepancy between servers is typically 5–10 µs/s and up to 30 µs/s. — [USENIX NSDI'18, Geng et al.](https://www.usenix.org/conference/nsdi18/presentation/geng)
  - **Accord** requires the cluster to know the max clock skew "through some secondary mechanisms." Its fast-path guarantee can fail if a coordinator stalls. — [CEP-15](https://cwiki.apache.org/confluence/spaces/CASSANDRA/pages/188744725/CEP-15+General+Purpose+Transactions)

### Inferences
- **Agreement and real-time order depend on different things.** Agreement among readers on the order does **not** depend on clock accuracy: a bad clock only distorts *which* order is chosen, never whether readers agree. Real-time order across writers **does** depend on clocks. It holds only if every node's true clock error is within the ε used for the ack wait. A node with a bad clock silently violates real-time order unless it fences itself (CRDB self-terminate, ClockBound interval checks).
- **Cost of the ack wait in precog.** With AWS PHC/ClockBound (ε ≈ 40 µs reported typical bound), an ack wait of ε adds tens of µs. That is far below group-commit latency, so external consistency for acked appends costs almost nothing on EC2 PHC-capable instances. With NTP (ε ≈ 100 µs on AWS, or 100–250 ms on generic NTP per CRDB), the wait is still small on AWS but prohibitive with generic NTP. These are estimates.
- **Stamp after durability.** If a node stamps on receipt but acks only after 2/3 durability, the commit-wait condition must be checked against the stamp time. Durability normally takes longer than ε, so the wait is usually already satisfied.

- Current (2024–2026) Google TrueTime ε figures were not found in a fetched primary source this session.
- Whether ClockBound exposes the PHC bound automatically in its current version was not verified.

## Q4. Which approach is simplest on top of a leaderless durable-write layer, and what minimal coordination remains?

### Takeaway
The simplest option is node-stamped HLC plus a periodic per-node durable watermark, with min-watermark delivery at readers. This is the CRDB closed-timestamp / TiKV resolved-ts pattern with "range leaseholder" replaced by "ingest node." It needs no per-entry coordination. The irreducible coordination is a consensus-backed membership/epoch service, used only for changes. That service must (1) admit nodes at an agreed starting watermark, and (2) on failure, seal the failed node's epoch at an agreed final watermark and entry set, and fence it. Add an ε clock bound with self-fencing if real-time order is wanted. Dependency-based leaderless protocols (Accord, Tempo, EPaxos family) also avoid a leader, but they add quorum rounds per command and complex recovery. They are much more machinery than an append log needs when entries do not conflict semantically.

### Cited Findings
- **Accord** uses HLC timestamps made unique by appending the replica ID. In PreAccept the coordinator proposes t0, and replicas accept it or return a higher t. The fast path needs a fast-path quorum per shard with t = t0. The slow path proposes the max t to a simple majority. Dependency sets may differ across coordinators and replicas but must be supersets of the transactions that can commit at lower t. Fast-path electorates can shrink: for every two nodes excluded, one fewer vote is needed. Recovery gathers state from a simple quorum. The CEP claims strict serializability, with proofs "to be published at a later date," and says the prototype was tested with Maelstrom. — [CEP-15](https://cwiki.apache.org/confluence/spaces/CASSANDRA/pages/188744725/CEP-15+General+Purpose+Transactions)
- **EPaxos limitation, as stated by the Accord authors.** EPaxos was the first leaderless protocol with a fast path, but "suffers from high contention as every fast path participant must have witnessed every dependency." — [BigDataWire on CEP-15](https://bigdatawire.com/2022/10/14/cassandra-to-get-acid-transactions-via-new-accord-consensus-protocol); [CEP-15](https://cwiki.apache.org/confluence/spaces/CASSANDRA/pages/188744725/CEP-15+General+Purpose+Transactions)
- **Accord authors:** Elliott Smith, Zhang, Eggleston, Andreas (Apple and Univ. of Michigan). Integration into Cassandra was ongoing as of 2022 reporting. — [BigDataWire](https://bigdatawire.com/2022/10/14/cassandra-to-get-acid-transactions-via-new-accord-consensus-protocol)
- **Tempo** claims higher throughput and more predictable performance under contention than prior leaderless SMR, in geo-distributed tests. The abstract gives no numbers. — [arXiv:2104.01142](https://arxiv.org/abs/2104.01142)
- **CRDB closed timestamps** are issued by the Raft leaseholder, so the "who promises" role is consensus-backed. — [CRDB Follower Reads](https://docs.cockroachlabs.com/docs/stable/follower-reads)

### Inferences
- **Mapping onto precog.** Each ingest node already owns its own WAL, so it plays the leaseholder role for "entries stamped by node N." The per-node promise "no more stamps ≤ W_N" is local, needs no consensus, and matches CRDB's "push late writes above the closed timestamp."
- **Relation to Scalog.** The HLC/watermark scheme is Scalog with the per-cut Raft commit removed from the steady state. Scalog commits every cut through Raft, which makes failure handling uniform: the cut itself defines what is in. The HLC scheme commits only membership/epoch changes, so the steady state has lower latency and no consensus. The cost is a separate, rarely exercised seal/recovery path that must be implemented correctly, and that path is where bugs would hide.
- **Producer clocks are not needed.** A writer's own (epoch, seq) order is preserved if each writer's batches go through one node per epoch, or if nodes stamp max(HLC, last stamp for this writer + 1). The second rule needs the stamping node to know the writer's previous stamp, which is a design question for precog.
- **Accord/Tempo-style protocols** would only pay off if precog needed conflict-aware ordering (e.g., per-key transactions). For a pure append log where all entries are mutually ordered, Tempo's stability condition reduces to min-watermark anyway. That is an inference.

### Gaps
- EPaxos (SOSP'13), Atlas (EuroSys'20), Caesar (DSN'17) and Janus (OSDI'16) were not fetched, so they have no cited mechanism or latency figures here.
- The Accord arXiv paper with measured latency was not located. The search returned only the CEP whitepaper, and the PDF returned 503.
- No published evaluation of the "HLC-stamp + watermark + consensus-only-on-membership" design as a log ordering layer was found. Scalog (NSDI'20) would be the comparison point and is covered by another researcher.
